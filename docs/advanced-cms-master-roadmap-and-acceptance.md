**Version:** 2026-10-27 · **Owner:** DentaSmart CMS/SEO workstream\

**Status:** Planning and isolated test implementation only; **NOT production-authorized**\
**Important:** This is the authoritative task register for the Advanced CMS, the separate Blog Editor's SEO parity, and associated publishing/technical SEO integration. Update this file after each verified milestone so no agreed work is lost.

## How to use this register

- Work through **NEXT** in this exact order: **(1) D0 read-only Toothache baseline audit; (2) C1/C2 Phase 8/9 P0 safeguards and acceptance; (3) D1–D7 Phase 10 implementation; (4) E Phase 11 QA; (5) F separately authorized release**. D0 makes no publication/data changes and may precede editor defect fixes; do not begin D1 publishing writes before C1 safeguards.
- Statuses: `[x]` = verified in the isolated testing environment with documented evidence; `[ ]` = not fully verified/remaining. "Implemented" does **not** equal "live," "publicly published," or "tested end-to-end."
- After each task, record commit SHA, test commands/results, browser evidence, blockers, and the **next exact task** under Progress Log. Do not silently skip open tasks or count partial QA as complete.
- **Strict isolation:** Test repo/branch, Codespace `didactic-succotash`, isolated local MySQL `dentasmart_test` on port 3307; no live site, production DB/storage, DNS, `robots.txt`, sitemaps, default/main branch, or production deployment without a separate authorization.
- Preserve **all existing blog content/metadata/status** (including nullable SEO, OG, canonical, category, tags, images, legacy keywords and reviewer fields); no bulk rewrites, migrations, clinical attribution or unapproved publishing.
- Do **not** run Save Draft on an existing published blog until the published-to-draft transition is fixed and verified. Use disposable drafts for browser QA. Keep test reviewer identity explicitly synthetic.

## D. Phase 10 — Publishing, public SEO, URL lifecycle and sitemaps (strict order)

### D0. Read-only Toothache pilot audit — **NEXT technical investigation**
- [ ] Inspect Toothache public test-route owner, source fallback, saved and test-published revisions, server-rendered HTML, hydration, SEO title/description, canonical, robots/noindex, schema, OG/featured images, reviewer eligibility and test sitemap.
- [ ] Trace server route/sitemap/redirect ownership and CDN/XML reachability; retain existing `server/seo.ts`, `server/redirectsRouter.ts`, `server/redirectCache.ts`, and test-only `server/cmsTestPublication.ts` where safe. Do not build duplicate systems.
- [ ] Verify source page restoration on withdrawing Toothache snapshot and no private draft leakage; record a route ownership matrix and gaps **before making publisher edits**.

### D1. Design safe ownership & publishing contracts
- [ ] Define permitted CMS-owned vs source-controlled routes and adapters, no collisions with Blog Editor, no published route replacing an unsupported static page without verified content equivalence.
- [ ] Define explicit draft, published, unpublished, archived/withdrawn, deleted and redirect states; revision locks, RBAC, change approval, content validation and audit log.
- [ ] Define expected behavior for removed URLs (301 only with relevant public replacement, otherwise appropriate 404/410; don't redirect everything to homepage). Source-controlled fallback must be explicit.
- [ ] Test handling of duplicate path, slug, root/cross-hub ownership, trailing slash, canonical conflicts, broken targets, malicious/external redirect and rollback.

### D2. Integrate CMS content and metadata into controlled public HTML
- [ ] Server-render/test-serve **only a verified published CMS snapshot**, not editor preview or unsaved/private drafts.
- [ ] Serve correct visible content and title/H1, description, OG/X values where actually supported, public image links/ALT, canonical, schema.org JSON-LD and verified reviewer metadata.
- [ ] Integrate automatic and manual JSON-LD into controlled public renderer; ensure sitewide `Organization`/`WebSite` remains server-owned and there are no conflicting duplicate page/article entities.
- [ ] Verify clinician identity, credentials, public profile, actual clinical review and date out-of-band; QA dummy data must never appear publicly. Gate unsupported medical/schema claims.
- [ ] Treat Codespace-only media (`/api/cms-test-media/`) as private testing assets; use authorized stable public media storage and verify accessible URLs before broader publication.

### D3. Publish/update/unpublish/delete state machine
- [ ] Enable only a controlled test extension of Toothache or next approved source-backed hub; after approval, expand to Conditions, Symptoms and Guides, then other hubs when adapters are safe.
- [ ] Keep authoring, draft saving and revision snapshots independent of public deployment; require explicit approval to change published content or visibility.
- [ ] `Publish` should atomically switch to eligible new version and update page state; `Update` should preserve URL, status and SEO settings unless explicitly changed.
- [ ] `Unpublish` should cease publishing the CMS snapshot; preserve draft/history and enforce correct fallback/404/410 behavior based on route ownership.
- [ ] `Discard Draft` on imported source overlays and `Delete Draft` on private unsaved-to-public work must **not** erase source-controlled live content. Production deletion and test media cleanup are separately gated.
- [ ] Restore revision with correct route, metadata, publication, redirect and indexing rules; use concurrency and rollback tests.

### D4. Automatic redirects and slug changes — reuse existing redirect admin
- [ ] On **approved rename**, first ensure new published URL serves correct 200/HTML/canonical; then activate **301 old URL → new public URL**.
- [ ] Validate duplicate/colliding URLs; self-redirect, chain/loop, target to draft/unpublished page, slash/case and external redirects. Consolidate chains when safe, not just warn.
- [ ] Correctly preserve query behavior, invalidate redirect caches, and verify old/new HTTP responses after rename/rollback.
- [ ] Preserve unrelated manually managed redirects. Never auto-create redirect merely from changing a draft's proposed slug.

### D5. Sitemaps, robots and indexability — automatic synchronization
- [ ] Include **only canonical indexable public URLs** in the correct segmented sitemap; exclude private drafts, explicitly unpublished/deleted pages, 3xx redirect sources, noindex pages and ineligible canonicals.
- [ ] Add eligible new public URL after successful publish; replace old URL on rename; remove upon noindex, unpublish and delete; restore on eligible republish.
- [ ] Reconcile existing redirect filtering with cache availability: current `getEnabledRedirectSources` falls back to an empty filter if cache is unavailable; design safer behavior/testing rather than claiming every redirect is always excluded.
- [ ] Apply actual page `robots` noindex/nofollow only to served HTML. Decide separately whether `robots.txt Disallow` is appropriate; do not combine indiscriminately with noindex because crawlers must access HTML to see noindex.
- [ ] Prevent sitemap inclusion of noncanonical or withdrawn pages; handle canonical override conflicts, sitemap generation/cache invalidation, and `/sitemap-index.xml`/segmented XML reachability through deployment/CDN. See `sitemap-diagnosis.md` for an earlier XML interception concern.
- [ ] Cross-check generated `<loc>` against HTTP status (eligible 200), robots/noindex and canonical. Separate static/scheduled sitemap generator `generate_sitemap.cjs` must not overwrite authoritative dynamic behavior unexpectedly.

### D6. Internal links, SEO QA and CMS hub rollout
- [ ] Identify inbound internal links to renamed/withdrawn URLs; propose safe update to final canonical destinations; retain link audit and 404 tracking. Do not silently mass-rewrite published content.
- [ ] Verify no redirect loops/chains, link breakage, orphaned indexed pages, duplicate canonicals, 404s or invalid sitemap entries after transitions.
- [ ] Incremental per-hub import/render equivalence: Conditions, Symptoms, Guides first, then Treatments, Costs, etc. **Compare every source page against CMS import and served output for exact text, case, punctuation, heading labels, H1–H4 hierarchy, AEO micro-blocks, sections/order, links, CTAs, image/ALT and SEO metadata; do not regenerate human-authored headings from lowercase keyphrases or drop supplemental content.** Known Toothache discrepancies to resolve: source heading **“Understanding Toothache”** became **“Understanding toothache”** via `cmsConditionAdapter.ts` primaryKeyword; live **“In one sentence:”** section from `aeoConditions[slug].inOneSentence` is missing in CMS import/renderer. Other public hubs stay read-only until proven safe; Blogs remain in independent Blog Editor.
- [ ] Add/verify blog-specific public robots/noindex/slug/301 handling and X metadata only under separately approved schema/API changes; preserve all existing blog post fields/status.

### D7. Phase 10 controlled end-to-end acceptance
- [ ] Test cases: new draft (no public URL); publish 200; update; rename old 301/new 200; sitemap switch; noindex/exclusion; unpublish/withdrawal; delete/404/410; revision restore; republish; invalid action; permissions and rollback.
- [ ] Each case must verify HTTP response, **served** title/description/canonical, rendered content, JSON-LD entities, robots, sitemap, redirect cache and internal links; record screenshots/logs and test assertions.
- [ ] Ensure separate Blog Editor functions unchanged; no private or QA reviewer/image URLs leak. **No live publishing** in Phase 10 test work.
- [ ] Phase 10 sign-off only after all critical items pass and no P0 data-loss/indexing risks remain.
